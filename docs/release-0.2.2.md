# 0.2.2：零组间距与道路连通检查

目标组间距改为 0，组内间距保持配置值。贴合允许，重叠禁止。
候选位置只有在所有已放置床位和新增床位都能通达场地边界时才会被接受。
不通过时尝试下一个位置或方向，再按现有规则拆为更小的合法组合；无解的模块计入未放置数量。
算法仍为按评分选择位置的贪心算法，不保证全局最优装箱数量。

## 为什么原检查漏报

原实现把整个场地和模块外接矩形也列为道路，再检查床位周边是否与道路相交。
床位天然在场地内，所以该条件几乎总是成立，不能识别被其他床位围住的区域。
取消原来的组间距后，原先被间隔掩盖的堵路问题更容易出现。

当前模型将“场地减去床位占用”作为潜在通行空间。
仅与场地边界共享非零长度边的连通分区视为可达区域，角点接触不算通路。
每张床都必须与可达区域共享非零长度边；新增模块不能切断已有床位的通路。
检查使用与 API 坐标相同的毫米精度，防止浮点裂缝被误判为道路。

这是现有配置下的几何连通检查。配置尚未描述墙、柜体障碍、指定出入口和最小净宽，
因此不能根据贴图推断这些条件，也不代表已经验证实际通行宽度。

最终结果始终执行连通审计，即使显式传入 `road_check=False`，也不会把不通过的结果标为成功。
此开关仅用于诊断时停用候选过滤。API 的 `metrics.road_connected` 和
`beds_without_road_access_count` 返回最终检查状态；小程序显示该状态。
道路返回 `polygon_m` 与 `holes_m`，孤立空地标为 `isolated_open_area`，不计入可达道路面积。

## 实际测试结果

![64床对比](release-0.2.2/roads_before_after.png)

- D2/G12/C4、20×30 m：仅取消间距时 64 床中 7 床不通达；加入候选连通检查后仍是 64 床，0 床不通达。
- U 形场地、B4：两个贴合的双模块组，实际 8 床，无越界和堵路。
- A26/B4/C2/D4、30×45 m：实际 100 床、36 模块，全部通达。
- 160 组随机混合布局：独立重建床位几何检查，无堵路、重叠、越界和床位数量丢失。
- 28,000 次边界判断与独立几何库结果一致；105 个布局场景、32 个组内几何场景通过。
- 27 项 Python 回归、3 项预览 JavaScript 测试、3 项端到端用例通过。
- 前端 28 项 Node 测试通过；异常测试模拟 SDK/HTTP 返回，未调用真实云服务。

## 本机耗时

布局耗时是进程内重复三次的中位数，图片渲染单独计时，贴图缓存已预热。
硬件及运行环境保存在 [benchmark.json](release-0.2.2/benchmark.json)。

| 场景 | 不过滤堵路候选，秒 | 开启连通检查，秒 | 一张贴图 PNG，秒 |
| --- | ---: | ---: | ---: |
| 64 床混合反例 | 0.0701 | 0.1146 | 0.2230 |
| 100 床混合 | 0.0562 | 0.0741 | 0.1516 |
| 300 床 B | 0.1963 | 0.5617 | 0.5951 |
| 300 床 G | 1.8894 | 3.1931 | 1.6809 |

两列布局时间均包含最终审计；左列仅用于性能对照，可能产出堵路结果。
优化包括缓存已放床位并集、复用已通过候选的几何、预计算排序数据、批量矩形碰撞检测，
以及按评分依次校验、遇到第一个合法候选即停止。
优化前同机单次 300 床 G 布局约 7.58 秒，优化后三次中位数约 3.19 秒。

这些数据不含进程冷启动、网络、上传、云端 CPU 配额或并发排队。
若额外输出结构校对图，还需要第二次渲染。没有部署或测量云端。

本次同时包含已校对的边界/凹形场地、四个正交旋转方向、B 床位 1 mm 越界、
G 床头方向以及小程序错误状态与下载加载状态修复。
